# التسنيم المكي (Tasneem Al-Makki)

Water-package e-commerce site for Mecca, Saudi Arabia. **Arabic-only, RTL, mobile-first.**
Customers sign up with name + phone, pick water packages, check out with a map pin
inside the delivery zone, and track the order. The owner manages order status from a
Google Sheet and gets a Telegram message on every new order.

- **Live:** https://tasneem-shop.vercel.app (auto-deploys `main` on every push)
- **Repo:** https://github.com/ember3324/tasneem (**public** — never commit secrets or personal data)
- **Status:** test phase. Every order currently in the database is test data. No real customers yet.
- **Owner:** Hani. A second person also works on the project (taking turns in the same Dropbox folder).

## 1. Read this first (for Claude agents)

1. **This is not the Next.js you know.** Next.js 16.3 has breaking changes versus older
   versions: `proxy.ts` replaces `middleware.ts`, `params`/`searchParams` are Promises,
   routes are typed through the global `PageProps<'/route'>` / `LayoutProps<'/'>` helpers
   (generated by `npx next typegen`). Read `AGENTS.md` and check
   `node_modules/next/dist/docs/` before assuming how caching, routing or config behave.
2. **Private operational notes live in `HANDOFF.txt`** (account inventory, IDs, phone numbers
   of the admin/test logins, gotchas). It is gitignored on purpose because the repo is public.
   It exists in the shared Dropbox folder but not on a fresh GitHub clone. `CLAUDE.md`
   imports this README and `HANDOFF.txt` automatically.
3. **Do not commit or push unless the owner says so** ("push it" / "push it live"). The working
   agreement is: implement → verify locally → owner reviews → they say push → commit, push,
   then confirm the Vercel deployment reaches *Ready*.
4. **Secrets live only in `.env.local`** (gitignored). Never print their values in chat and
   never write them into tracked files, scripts you leave behind, or commit messages.
5. **The database is shared by local dev and production.** There is one Supabase project.
   Whatever you write while testing locally is live data. Clean up test rows afterwards, and
   prefer read-only checks.
6. **Match the surrounding code.** Keep comment density, naming and idioms consistent with the
   file you are editing. Explain *why* in comments, not *what*.
7. **Arabic only.** Every customer-facing string is Arabic. Do not add English UI.
8. **Verify before claiming done.** Run the checks in [§11](#11-testing-and-verifying-changes);
   for UI work, actually load the page (mobile width first) rather than assuming.

## 5. How the app works

### 5.1 Authentication (deliberately minimal)

- `signUpOrLogIn` (`src/lib/actions/auth.ts`): the phone is normalised to E.164 by
  `normalizeSaudiPhone` (`src/lib/phone.ts` — accepts `05xxxxxxxx`, `5xxxxxxxx`, `9665…`,
  `+9665…`). If a profile with that phone exists the user is logged in; otherwise a name is
  required and a profile is created. **No password, no OTP.** Anyone who knows a phone
  number can log in as it — accepted MVP trade-off, documented in `session.ts`.
- The session is `<profileId>.<HMAC-SHA256(profileId)>` in an `httpOnly`, `sameSite=lax`,
  `secure`-in-production cookie named `session`, valid 180 days.
- `getCurrentProfile()` (`src/lib/profile.ts`) is the `auth.getUser()` equivalent. It is
  wrapped in React `cache()` so the layout and the page share one query per request.
- **Consequence for data access:** `auth.uid()` is always null, so RLS cannot scope anything.
  Every table except the public catalog has RLS *enabled with no policies* (safe default for
  the anon key), and **all queries go through the service-role client**
  (`createAdminClient()`), with authorization enforced in application code. **Any query that
  touches user data must filter by `profile.id`** (see `cart.ts`, `address.ts`, `checkout.ts`
  for the pattern: `.eq('user_id', profile.id)`).
- `src/proxy.ts` redirects unauthenticated requests for `/checkout`, `/orders`, `/account`,
  `/admin` to `/login?next=…`. `src/app/admin/layout.tsx` additionally requires
  `profiles.is_admin = true`.

### 5.2 Catalog and storefront

- `src/lib/catalog.ts`: `getAllProducts()` and `getProductBySlug()` wrapped in
  `unstable_cache` (120 s). The cache is also persisted to disk in `.next/cache`, so after
  changing products in the database delete `.next/cache` (or wait two minutes) to see it.
- The shop is a **flat grid of all products** at `/categories` (a leftover URL name — `/`
  redirects there). There is no category-picking step.
- `products.category_id` is NOT NULL, so **one hidden category row** (`باقات السقيا`) still
  exists. It is never shown. Treat it as plumbing.
- Current products (from `products/nabaa-makiyoon-pricelist.docx`; photos in `public/products/`):

  | # | Name | Slug | Unit | Price (SAR) |
  |---|---|---|---|---|
  | 1 | طل | `makyoon-saqya-tall` | 10 شرنك | 135 |
  | 2 | ديمة | `makyoon-saqya-dimah` | 50 شرنك | 510 |
  | 3 | وابل | `makyoon-saqya-wabil` | 100 شرنك | 990 |
  | 4 | صيب | `makyoon-saqya-sayyib` | 300 شرنك | 2,730 |
  | 5 | غيث | `makyoon-saqya-ghaith` | 500 شرنك | 4,450 |
  | 6 | مزنة | `makyoon-saqya-muznah` | 1000 شرنك | 8,750 |

  One **شرنك (shrink) = 20 bottles of 330 ml**. Packages are named after rain words, smallest
  to largest. A seventh 17,000 SAR product was deliberately removed.
- The product card shows the static label **"مياه 330 مل"** (hard-coded in
  `src/app/(shop)/categories/page.tsx`), not the product name; the package name appears on
  the product detail page.

### 5.3 Cart

`cart_items` is per user, `unique(user_id, product_id)`. Server actions in
`src/lib/actions/cart.ts`: `addToCart` (adds to the existing quantity), `updateCartQuantity`
(`<= 0` deletes), `removeFromCart` — all scoped to the session's profile. The cart UI
(`cart-items.tsx` / `cart-line-item.tsx`) is optimistic (`useOptimistic`), and the quantity
is an editable field capped at **99,999** (`MAX_QUANTITY` in `cart-line-item.tsx`) so large
orders don't require tapping "+" repeatedly.

### 5.4 Addresses and the service-area check

- Customers drop a pin on a Mapbox map (`location-picker.tsx`, default view = the Grand
  Mosque) or use "my location". `saveAddressAndCheckServiceArea` stores the address with
  `in_service_area` computed by `isWithinServiceArea` (`src/lib/geo.ts`: turf
  `booleanPointInPolygon` against every `service_zones` row where `active = true`).
- Saved addresses are listed first at `/checkout/address` with a "deliver here" button, so
  repeat customers skip the map. Out-of-area addresses show their status instead.
- The check runs **twice**: when the address is saved, and again in `createOrder` against the
  *current* zones (zones may have changed since). Malformed polygons are treated as "outside".
- Deleting an address used by a past order works because migration `0002` changed
  `orders.address_id` to `ON DELETE SET NULL`.

### 5.5 Checkout and order creation

`createOrder` (`src/lib/actions/checkout.ts`), in order:

1. Validate address (owned by the user, inside a zone) and payment method (`cash` | `card`).
2. Read the cart; compute total and an `items_summary` string (`"2x طل; 1x ديمة"`).
3. Insert `orders` (number `WB-XXXXXXXX`, snapshot of customer name/phone/coordinates/items),
   then `order_items` (snapshot of product name and price), then empty the cart.
4. **Best-effort, independent try/catch blocks** — neither can fail the checkout:
   append a row to the Google Sheet and store `sheet_row_number`; send the Telegram message.
5. Redirect: cash → `/orders/<number>`; card → `/checkout/pay/<number>`.

Orders snapshot everything they display, so later edits to products or addresses never
change history.

### 5.6 Order status and the Google Sheet

- Statuses: `pending → confirmed → out_for_delivery → completed`, or `cancelled`. Arabic
  labels are the `status.*` keys in `translations.ts`
  (قيد الانتظار / مؤكد / قيد التوصيل / مكتمل / ملغى). The order page shows a 4-step timeline.
- A DB trigger writes every status change to `order_status_history`.
- **Sheet layout** (tab must be named exactly `Orders`; row 1 is the header):

  | Col | Header | Notes |
  |---|---|---|
  | A | Order ID | join key = `orders.order_number` |
  | B | Customer Name | |
  | C | Phone Number | |
  | D | GPS Coordinates | `"lat, lng"` |
  | E | Items | `items_summary` |
  | F | Total (SAR) | |
  | G | Payment Type | `Cash` / `Credit` |
  | **H** | **Status** | **admin-edited**: `Pending`, `Confirmed`, `Out for Delivery`, `Completed`, `Cancelled` (case-insensitive; anything else is ignored) |
  | **I** | **Proof Photo URL** | **admin-edited**: public image link; shown to the customer once the order is `completed` |
  | J | Created At | |
  | K | Address Details | optional free text |

  **Only ever append new columns at the end.** `fetchSheetUpdates()` reads H and I by fixed
  index; inserting a column mid-sheet silently breaks the sync.
- **Sync direction.** DB → Sheet happens only once, when the order is created. Sheet → DB is
  polled: `GET /api/cron/sync-sheet` reads every row and, for each order whose Sheet status or
  proof URL differs from the DB, updates the DB. It authenticates with `?secret=<CRON_SECRET>`
  (or `Authorization: Bearer`). **cron-job.org** calls it every 2 minutes. The GitHub Actions
  workflow in `.github/workflows/sync-sheet.yml` is dead weight (GitHub's scheduler never fired
  reliably) — leave it or delete it, but do not try to fix it.

### 5.7 Telegram notifications

`src/lib/telegram.ts` posts an HTML message to the owner's Telegram group on every new order:
order number, customer, phone, bulleted items, total, payment method, optional address
details, and a Google Maps link built from the pin. The message text is currently **English**.
Failures are swallowed (logged) so they never block checkout. If this sandbox cannot resolve
`api.telegram.org` that is a local networking quirk; production is unaffected.

### 5.8 Payments (Moyasar) — built, not live

Flow, per `src/lib/moyasar.ts`: the pay page (`/checkout/pay/[orderNumber]`) renders Moyasar's
hosted card form → on completion the browser calls `POST /api/payments/link` to store
`moyasar_payment_id` → Moyasar redirects to `GET /api/payments/callback`, which **re-fetches
the payment from Moyasar's API** and checks status/amount/currency before marking the order
paid and moving `pending → confirmed` → `POST /api/payments/webhook` is the authoritative
async confirmation (verified by comparing `secret_token` to `MOYASAR_WEBHOOK_SECRET`).
Amounts are converted SAR → halalas (`toHalalas`). Without `NEXT_PUBLIC_MOYASAR_PUBLISHABLE_KEY`
the pay page shows an English "Payments are not configured yet" message. See §13 for
problems to fix before this goes live.

### 5.9 Admin

One admin profile (`is_admin = true`). `/admin/zones` is a Mapbox polygon editor
(create / toggle active / delete) backed by `src/lib/actions/zones.ts`, each action
re-checking `is_admin`. The admin chrome is English and minimal. Everything else —
order status, products, data cleanup — happens in the Google Sheet, the Supabase
dashboard, or one-off scripts (§10).

### 5.10 Policies pages

`/policies/{returns,terms,privacy}` render the owner's three Arabic legal texts. The
source of truth is the `.txt` files in `/policies`; `src/lib/policies.ts` embeds them
**verbatim** as string constants (so there is no runtime file read / Vercel file-tracing
dependency). `parsePolicy()` in the same file splits the text into title, "last updated"
line and blocks (headings, bullet lists, numbered lists, paragraphs), and
`src/components/shop/policy-content.tsx` renders those blocks. If the `.txt` files change,
copy the new text into `policies.ts`. The footer links to all three.

## 6. Data model

Defined in `supabase/migrations/0001_init.sql` (+ `0002`). Both are applied to the live DB.
New schema changes = a new numbered migration file, run in the Supabase SQL editor.

| Table | Key columns | Notes |
|---|---|---|
| `profiles` | `id`, `full_name`, `phone` (unique, E.164), `is_admin` | The account. Not linked to `auth.users`. |
| `addresses` | `user_id`→profiles (cascade), `label`, `address_line`, `lat`, `lng`, `in_service_area` | `city` and `is_default` are legacy/unused. |
| `service_zones` | `name`, `polygon` (GeoJSON Polygon, `[lng,lat]`), `active` | Public-read when active. |
| `categories` | `name`, `slug`, `sort_order` | One hidden row; see §5.2. |
| `products` | `category_id` (NOT NULL), `name`, `slug`, `price`, `unit`, `image_url`, `in_stock`, `sort_order`, `description` | Public-read. `in_stock=false` shows "out of stock" instead of the button. |
| `cart_items` | `user_id`, `product_id`, `quantity > 0`, unique pair | |
| `orders` | `order_number` (unique), `user_id`, `address_id` (nullable), denormalised customer/location/items/total, `payment_method` (`cash`/`card`), `payment_status` (`pending`/`paid`/`failed`/`cod_pending`), `status`, `proof_photo_url`, `moyasar_payment_id`, `sheet_row_number`, `sheet_synced_at` | |
| `order_items` | `order_id` (cascade), snapshot `product_name`, `unit_price`, `quantity`, `line_total` | |
| `order_status_history` | `order_id`, `status`, `changed_at` | Filled by the `on_order_status_change` trigger. |

The seed data in `0001` (old categories/tissues/miswak) was replaced by the real catalog; the
migration file was intentionally left as the historical schema.

## 8. UI and design conventions

- **Arabic only.** All strings are keys in `src/lib/i18n/translations.ts` (flat dictionary,
  grouped `nav.`, `shop.`, `cart.`, `checkout.`, `address.`, `account.`, `orders.`, `status.`,
  `auth.`, `whatsapp.`). `getLocale()` always returns `'ar'`; the `t(locale, key)` /
  `useLocale()` plumbing is kept so a second language could be reintroduced. Root layout sets
  `<html lang="ar" dir="rtl">`.
- **Bidi pitfall (cost us two bugs):** never put `dir="ltr"` on a container that has Arabic
  text — it scrambles word order. Wrap only genuinely Latin/numeric fragments (prices such as
  `135.00 SAR`, order numbers, phone numbers, coordinates, quantity inputs, `2x`) in their own
  `<span dir="ltr">`.
- **Colors** (`globals.css`): `ocean-50…900` is a soft, desaturated accent scale used for
  borders and bevels; `brand-400…700` is a more vivid blue reserved for CTAs and the active
  nav pill, so primary actions pop. Body background `#f7fafb`.
- **Layout** (`src/app/(shop)/layout.tsx`): a flex column with a sticky-footer pattern —
  static header (scrolls away) → hero card → `<main>` → site footer → fixed bottom nav
  (`pb-16` reserves its space) → floating WhatsApp button (`bottom-20`, above the nav).
- **Header / bottom nav / footer backgrounds** (`headerbg.jpeg`, `footerbg.jpeg`): solid white
  base + a translucent white gradient over the image (≈60% image visibility) with
  `cover`/`center`. Use that technique rather than plain `opacity`, so scrolled content never
  bleeds through the fixed nav.
- **Bottom nav** (`bottom-nav.tsx`): shop / orders (logged in) / cart (with count) /
  account + logout, or login. Active tab = filled `brand-600` pill with white text; inactive =
  neutral icon + label.
- **Hero**: `public/hero.jpeg` in a bordered rounded card, centred at 78% width.
- **Product cards**: two per row at every width, `rounded-xl bg-white shadow-md`, square image
  with `object-contain` (always show the whole picture — never crop products), centred stack
  of label → unit (with package icon) → price → solid blue "add to cart" button.
- **Animation**: only `.animate-fade-in-up` (staggered per card), disabled under
  `prefers-reduced-motion`.
- **Brand**: the site name stays "التسنيم المكي". Do not add taglines unasked.

## 10. Runbooks (how do I…)

Most data tasks are done in the **Supabase dashboard** (Table Editor / SQL Editor) or with a
throw-away script (see §11). Changes to products appear within ~2 minutes (cache).

**Change a product's price, name, unit or stock** — Supabase → Table Editor → `products`.
(The card label "مياه 330 مل" is code, not data.)

**Add a product** — copy the image into `public/products/` (JPEG/WebP, re-encode large PNGs
with `sharp`), then insert a `products` row: unique `slug`, `price`, `unit`
(`"N شرنك"`), `image_url` (`/products/<file>`), `sort_order`, and `category_id` = the id of the
single existing category. No code change needed.

**Reorder products** — change `sort_order`.

**Change a delivery zone** — log in as the admin → `/admin/zones` → draw a polygon (Mapbox
Draw), name it, save; toggle `active` or delete old ones. At least one active zone must exist
or no address can pass checkout.

**Change an order's status** — edit column H in the Google Sheet. It reaches the DB (and the
customer's order page) within ~2 minutes. Paste a delivery-photo URL in column I and set the
status to `Completed` to show proof to the customer.

**Make someone an admin** — they sign up through the site first, then in the SQL editor:
`update profiles set is_admin = true where phone = '+9665XXXXXXXX';`

**Wipe test data but keep the admin** (run in this order — FKs):
```sql
delete from order_status_history;
delete from order_items;
delete from orders;
delete from cart_items;
delete from addresses;
delete from profiles where is_admin = false;
```
The Sheet is not cleared by this; stale rows are ignored by the sync (it skips order ids not
in the DB), but delete them by hand for tidiness.

**Deploy** — push to `main`. Vercel builds automatically (~35 s). Confirm in the Vercel
dashboard that the deployment is *Ready* (open the deployment's detail page; the list view can
show a stale "Building").

**Roll back** — Vercel dashboard → Deployments → promote the previous *Ready* deployment, then
`git revert` the bad commit.

**Add or change an environment variable** — update `.env.local` *and* Vercel → Project →
Settings → Environment Variables, then redeploy.

**Rotate a secret** — regenerate at the provider, update `.env.local` + Vercel, redeploy.
`CRON_SECRET` also lives in the cron-job.org job URL; `SESSION_SECRET` rotation logs everyone out.

**Unpause Supabase** — free projects pause after ~7 days idle; the whole site errors until
you click *Restore/Unpause* in the Supabase dashboard.

**Update the policies** — edit the `.txt` in `/policies`, copy the new text verbatim into
`src/lib/policies.ts`, preview `/policies/<slug>`.

**Change the WhatsApp number** — `src/components/shop/whatsapp-button.tsx`.

## 11. Testing and verifying changes

There are no automated tests, so verification is manual and should be explicit.

- **Static checks:** `npm run lint`, `npx tsc --noEmit` (run `npx next typegen` first if
  route-type names are missing), and `npm run build` before declaring a change safe.
- **UI changes:** open the page **at phone width first (≈375 px), then desktop**. The preview
  pane's screenshots after scrolling are unreliable — prefer querying the DOM / page text, or
  a tall viewport for full-page shots. Check RTL text order, that nothing is cropped, and the
  fixed bottom nav doesn't cover content.
- **Data/logic changes:** write a throw-away script *outside the repo* (Claude's scratchpad)
  or a temporary `_x.mjs` in the project root that you delete afterwards, and run it from the
  project root so `node_modules` resolves:
  `node --env-file=.env.local script.mjs`. Use test phones only (the test customer, E.164
  `+966…`). Orders need `lat`/`lng` and a valid address.
- **Full happy path:** log in as the test customer → add a product → checkout with a saved
  address → choose cash → confirm the order page, the new Sheet row, and the Telegram message →
  change the status in the Sheet → within ~2 min the order page timeline advances. Then delete
  the test order/rows (§10).
- **After deploying:** verify in a **fresh tab**. A tab left open across a deploy runs stale
  client JS; `deploymentId` now forces a reload on the next navigation, but a fresh tab is the
  only unambiguous check. Prefer reading the actual network response over trusting a stale page.

## 12. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| Every page shows "Missing Supabase config" | `.env.local` missing or empty |
| Whole site errors / DB timeouts | Supabase free project paused → unpause in dashboard |
| Dev: "Jest worker encountered child process exceptions" | Stale Turbopack workers: kill all `node` processes, delete `.next/cache`, restart |
| Dev: TS "Cannot find name `PageProps` / `LayoutProps` / `AppRoutes`" | Run `npx next typegen` (delete `.next` first if it persists) |
| Changed products in the DB but the site still shows old ones | Catalog cache: wait ~2 min, or delete `.next/cache` locally |
| Arabic text appears scrambled / words in wrong order | A `dir="ltr"` wrapped Arabic text — move it onto just the Latin/number fragment (§8) |
| Order status changed in the Sheet but not on the site | Status text not one of the five values; cron-job.org job disabled/failing; `CRON_SECRET` mismatch (hit the sync URL by hand and read the JSON: `rowsRead`, `ordersUpdated`); wrong tab name (must be `Orders`) |
| New orders missing from the Sheet | Service account lost Editor access, key rotated without updating Vercel, or `GOOGLE_SHEET_ID` wrong (check function logs — failure is only `console.error`) |
| No Telegram message | Bot removed from the group, token/chat id wrong or unset (silently skipped) |
| Vercel build fails on "deploymentId … 32 characters" | Don't pass the full SHA; keep `.slice(0, 12)` in `next.config.ts` |
| Deleting an address fails | Fixed by migration `0002`; if it recurs, confirm `orders_address_id_fkey` is `ON DELETE SET NULL` |
| A teammate's push didn't deploy | Vercel Hobby limits deployments to the account owner's linked identity in some setups; check the Vercel deployment's status/log |

## 13. Known issues and open items

1. **Card payment is not usable.** No Moyasar account/keys, yet `card` is the *default*
   option in `src/components/checkout/checkout-form.tsx` (`useState<'cash' | 'card'>('card')`).
   A customer who doesn't change it reaches a dead-end English error page. Until Moyasar is
   configured, default to cash or hide the card option. Setup steps: `SETUP.md` §3 (test mode
   first, then the webhook, then live keys after KYC).
2. **Unpaid card orders are already "real" orders.** `createOrder` inserts the order, appends
   the Sheet row and sends the Telegram message *before* payment. An abandoned card payment
   leaves a `payment_status = 'pending'` order that still shows in the Sheet and Telegram.
3. **Latent: Sheet sync can revert a paid order's status.** When Moyasar goes live, the
   webhook/callback sets `status = 'confirmed'` in the DB, but the Sheet still says `Pending`
   (the app never writes status back to the Sheet). The next sync run (≤2 min) sees a
   difference and sets the DB back to `pending`. Fix before launch: also update the Sheet's
   column H when the DB status changes, or make the sync ignore a Sheet value that hasn't been
   edited since the row was written.
4. **Sync does one DB query per Sheet row every 2 minutes**, and re-reads the whole Sheet each
   time. Fine for hundreds of orders; revisit (batching, or only recent rows) if volume grows.
5. **Telegram messages and the Google Sheet are in English** while the storefront is Arabic.
   Not changed because it was never requested.
6. **No phone verification** (see §5.1 / §14).
7. **Supabase free tier pauses after ~7 days idle.** Consider a keep-alive ping or paid plan
   before real customers.
8. **Vercel region** is Paris (`cdg1`); Dubai (`dxb1`) would be closer to Mecca once Vercel lets
   the Hobby plan select it.
9. Housekeeping: `sync-sheet.yml` (dead), unused default SVGs in `public/`, legacy columns
   `addresses.city` / `addresses.is_default`, and the product-category plumbing could be
   cleaned up.
10. Skipped from the reference design the owner supplied: a circular badge overlapping the
    header and carousel dots under the hero — can be built if requested.

## 14. Security notes

- **Auth is phone-only.** Anyone who knows a phone number can read that account's orders and
  addresses. Fine while the data is test data and low-sensitivity; add OTP (e.g. SMS) before
  scale. There is also **no rate limiting** on signup/login, so profiles can be created freely.
- **`signUpOrLogIn` redirects to a client-supplied `next` value without validating it** (open
  redirect). Restrict it to same-origin paths starting with `/` and not `//`.
- All data access uses the **service-role key**; correctness depends on every query filtering by
  `profile.id`. Review any new query with that in mind. Never import `createAdminClient` into a
  Client Component.
- The cron endpoint's secret is passed in the URL query for cron-job.org (it can appear in
  logs). Rotate it if the URL is ever shared. The route also accepts `Authorization: Bearer`.
- `.env.local` holds production secrets and the repo is **public** — the `.gitignore` entries for
  `.env*`, `*.serviceaccount.json`, the Google key JSON and `HANDOFF*.txt` are load-bearing.
  Don't weaken them. If a secret ever lands in a commit, rotate it — deleting the commit isn't enough.
- The proof-photo URL comes from a Sheet cell and is rendered with `unoptimized` `next/image`;
  only paste links you trust.

## 15. Working in the shared Dropbox folder

The project lives in a shared Dropbox folder (`.env.local` and all secrets included —
intentional). The two people who work on it **take turns and never work at the same time**, so
it is used as one working tree rather than separate clones.

- Before starting, let Dropbox finish syncing, then run `git status` — the previous person may
  have left uncommitted work or a half-finished change.
- Stop your dev server before you finish; don't leave one running against the folder.
- If `node_modules/` or `.next/` misbehave after switching PCs (native packages such as
  `sharp` / SWC are per-machine), run `npm install` and delete `.next/`.
- `.git/config` is shared, so commits are authored as the owner unless the collaborator sets
  their own `git config user.name` / `user.email` first. Pushing to GitHub still needs that PC
  signed in to a GitHub account with write access to the repo.
- Credentials the code needs are all in `.env.local`. Dashboard access (GitHub, Vercel, Supabase,
  Google Sheet, Telegram group) is per person — see `HANDOFF.txt` for what exists.

The project began as "AquaShop", then became "Tasneem", then "التسنيم المكي". 25 commits so far.

| Phase | What happened |
|---|---|
| Foundation | Phone-signup store, Mapbox service-area check, cart/checkout, Moyasar integration, Google-Sheet admin sync, bilingual i18n |
| Hardening | Cached catalog, parallelised Supabase calls, lazy-loaded Mapbox, region move to Paris, Telegram alerts, saved-address checkout, address-delete fix, `deploymentId` |
| Rebrand | Renamed to التسنيم المكي, **Arabic-only**, policies pages, real catalog from the price list, flat product grid (no categories), product photos |
| Redesign | Removed wallpaper; hero card; header/footer images; static header + fixed bottom nav with icons; smaller bordered cards (2 per row); softer ocean palette + vivid brand blue; restyle to match the owner's reference screenshot |

Decisions worth remembering, and why:

- **Phone-only auth, service-role everywhere.** Chosen for friction-free ordering in an MVP;
  consequences in §5.1 and §14.
- **Sheet is the admin panel.** The owner already lives in Google Sheets/Telegram; building an
  admin UI wasn't worth it. Cost: the one-way sync caveats in §13.
- **cron-job.org instead of Vercel Cron / GitHub Actions.** Hobby cron is daily-only and GitHub's
  scheduler never fired reliably.
- **Policies embedded as source**, not read from disk, to avoid Vercel file-tracing surprises.
- **`/categories` URL kept** for the flat shop to avoid breaking links/redirects.
- **Flat grid, no categories, "shrink" units** — the customer buys water by the shrink
  (20 bottles); simpler for the small catalog.
- **`deploymentId` from the commit SHA** so open tabs reload after a deploy instead of running
  stale client code.
